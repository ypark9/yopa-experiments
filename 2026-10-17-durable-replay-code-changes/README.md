# Does Lambda durable replay survive code changes? (Go SDK, local only)

Companion code and raw output for the yopa.page post
"Will a paused Lambda durable function survive your next deploy?" (2026-10-17).

Everything runs on one machine with the SDK's in-memory runner,
`durabletest`. No AWS account, no credentials, no network: `run.sh`
refuses to start if AWS credentials are visible, runs the harness with an
empty environment and AWS config pointed at `/dev/null`, and runs it inside a
network namespace with no interfaces (`unshare -rn`). Cost: $0.

## Versions

- Go 1.24.4 linux/amd64 for the harness
- `github.com/aws/aws-durable-execution-sdk-go` v1.0.0 (commit `e8c24d2a81bbd275fe53746b6c28e1ac08acd720`)
- `durablelint` from the analysis module at the same commit
  (`v0.0.0-20261015184945-e8c24d2a81bb`, built with go1.26.9 because the module needs Go 1.25+)

See `results/versions.txt`.

## What it does

`lab.Resume` starts an execution, lets the first invocation run until it
suspends on a one-hour `durable.Wait`, then swaps the handler and drives the
same execution (same checkpoint log) to the end:

```go
var version atomic.Int32
version.Store(1)
h := func(ctx durable.Context, e I) (O, error) {
	if version.Load() == 1 {
		return v1(ctx, e)
	}
	return v2(ctx, e)
}
r := durabletest.NewLocalRunner(durable.Handler[I, O](h))
first, err = r.Run(in) // one invocation: runs until the wait suspends it
...
version.Store(2)
final, err = r.RunUntilComplete(in)
```

- Group A (`cases/a0*`): the same code on both sides. Nondeterminism inside one
  version, which pinning a version does not remove. A09 is the safe control.
- Group B (`cases/b*`): v1 is `cases/bbase.V1` (validate, reserve, wait, charge);
  each case deploys a changed v2 while the execution is paused. This is what an
  execution started on `$LATEST` can see. B14 changes no code, only an
  environment variable read between operations.

Each case ran 20 trials per process, in 3 separate processes (60 trials).

Verdicts:

- `ok`: succeeded and the output is consistent.
- `silent`: succeeded, but the output is wrong. Group A: the key or total
  disagrees with what the first invocation checkpointed. Group B: the output
  differs from a fresh execution of the new code.
- `nde`: failed on replay with `NonDeterministicExecutionError`.
- `error:<type>`: failed on replay with another error.
- `first-run-error:<type>`: failed before any replay.

`golden_would_fail` is whether a golden-signature test (the
type/subtype/name/status list of a fresh run, the fields
`durabletest.AssertGoldenSignature` compares) differs from the recorded one.
For group B the recorded one is a fresh v1 run; for group A it is the first
fresh run of the same code in that process.

## Not tested

The real Lambda service. Everything here is the SDK's local runner; the
service may replay a different number of times (this harness replays twice
per execution, see `probes.txt`), and `ctx.RequestID()` is empty locally.
